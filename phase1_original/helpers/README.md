Use **legal_course_end_to_end_v1.ipynb** with **legal_course_helpers_v1.zip**. This is the single main run path. The ZIP contains readable helper source, the unchanged existing model, source notices and the existing frozen tokenizer. Earlier notebooks and active runs remain preserved separately. The tokenizer/ directory already supplies the frozen BPE; the older sample/canonical preparation ZIP is not needed. Platform detection checks Kaggle first; a /content directory alone does not identify Colab.

1. Colab: upload the notebook and the helper ZIP in a fresh runtime, then mount Drive in section 1. Kaggle: import the notebook, attach the helpers as a private Input. If Kaggle extracts them, set `HELPER_DIRECTORY` to the folder containing legal_scaffold/, tokenizer/ and source-version.json; leave `HELPER_ZIP` unset. The ZIP route remains optional. Select/install `torch` and `tokenizers`; preparation additionally needs `pyarrow`, optional gated downloads need `huggingface_hub`.
2. Select `ARCHITECTURE`: `gqa_pre`, `mla_pre`, `mha_pre`, or `mha_post`. Set a distinct `RUN_ID`. Set durable storage/cache paths. Select one GPU yourself for training or prediction; CPU preparation is supported. Kaggle output must be saved and read back before releasing the session.
3. Reuse complete verified WikiText cache or explicitly enable preparation. BPE never refits. The known TRAIN duplicate is excluded automatically; unintended overlaps stop the run. Either supply `WIKITEXT_STAGE` as a completed full stage, or enable one full WikiText pass. Keep an active older run in its original notebook until completion.
4. Supply the four official legal JSON files, or enable the gated download with a private `HF_TOKEN` secret. Colab: Secrets, allow notebook access. Kaggle: Add-ons → Secrets, enable notebook access and Internet yourself. No login or credential file is written. Sources are about 19.21 GB before windows/checkpoints; check storage capacity.
5. Reuse the four downloaded legal JSON arrays and enable token preparation. This retains duplicate documents and uses the frozen BPE and deterministic whole-document 90/10 split; identical text remains in the same partition. Exactly empty strings are skipped and counted. Missing/null/non-string/whitespace-only text and malformed records fail. No SQLite database or raw content hash walk is created. Small local uint16 shards commit to durable storage and a byte/record cursor about every 32 MB or 60 seconds, after a whole document. The new output directory is `legal-tokenize-only-v1`; preserve raw files, old partial preparation and checkpoints. After disconnection rerun with the same paths/output: completed records are not retokenized, only pending work repeats. Source size/mtime must stay unchanged.
6. After all four legal sources finish, fill `SOURCE_END_GROUPS` from source-end output lines (`source_index` 1–4, `next_record` 0, `committed_groups` N). The current observed Acts end is 12. The execution worker is capturing the other three values; do not guess. Use the same mapping/cache/order directory for all four architectures. Enable `PREPARE_MIXED_ORDER` on CPU once. It reads existing token-shard lengths, with no retokenization, to build one small fixed order index. Select the next window from the least-consumed source, so each source contributes about 25% of supervised tokens. Stop when any source exhausts; do not repeat or silently change the mix. Actual source availability/exposure is reported.
7. For each architecture select its own completed WikiText stage and distinct run ID. Set `LEGAL_TOKEN_TARGET = 100_000_000` and enable `RUN_LEGAL`. The first legal invocation uses the existing WikiText-weights-only initialization policy with fresh legal optimizer/scaler/scheduler and unchanged parent optimization settings. Use the new `legal-token-stages-v1` output root. Then set `LEGAL_RESUME` to that model's checkpoint, raise the cumulative target to 200M, 300M and later, and run again. Keep code, model, data order, settings and GPU/runtime fixed. Later stages preserve optimizer/scaler/scheduler/RNG/data cursor. Targets are stopping controls, not new optimizer identities. Failed AMP batches consume no tokens. A wall-clock stop before target produces a recovery; resume it with the same target.
8. Each target finishes its crossing batch and records actual supervised tokens. At batch size 2 and 1024 supervised positions/window, overshoot is at most 2,047 tokens. Receipts/metric logs report overshoot and cumulative per-source exposure. Milestone snapshots remain immutable and are never recovery-pruned. A token milestone does not claim full-epoch completion. The balanced order deliberately ends when the first source exhausts; its one-pass flag refers to that order, not every legal document.
9. Set `LEGAL_STAGE` to a reached milestone (assigned automatically after success), supply the official test, and enable prediction. Each actual cumulative token count gets a separate export directory; receipts include the target, actual count, source exposure and epoch status. The exporter keeps the existing 1,000 exact IDs, 512-word prompt and exactly 128 continuation-word contract. Only the root-prediction.json ZIP is submitted manually. Prediction time and model quality remain unmeasured here.
